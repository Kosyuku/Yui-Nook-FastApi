# 意识循环 / 主动消息 / 被动唤醒 v2 结构方案

> 最后更新：2026-05-01
> 目标：把“聊天必回”和“后台判断”彻底拆开，形成稳定的三层意识结构。

## 1. 结论先说

Yui Nook 现在的意识侧结构，定为三层：

1. 被动唤醒 / 事件注入
2. 主动消息检查 / 随机唤醒
3. 意识循环 / 日循环整理

这三层都不是聊天主链。

聊天主链单独算一层，规则一直很简单：

- 用户发来聊天消息
- 直接走大模型
- 无条件回复

所以完整运行图其实是四块：

- A. 聊天主链
- B. 被动唤醒
- C. 主动消息检查
- D. 日循环整理

其中真正属于“意识侧”的，是后面三层。

---

## 2. 总体原则

### 2.1 聊天和意识彻底分开

聊天一定回复，不做前置筛选。

意识相关任务都先由小模型做轻判断、轻整理，再决定要不要叫大模型。

### 2.2 大模型只做两类事

- 聊天正文
- 被小模型确认“值得继续”后的深输出

### 2.3 小模型负责脏活累活

- 事件值不值得管
- 当前要不要主动说话
- 最近状态要不要整理
- 哪些内容值得沉淀为长期记忆

### 2.4 成本和频率分层

从轻到重：

1. 事件触发
2. 主动消息检查
3. 日循环整理

从高频到低频：

1. 事件触发：随时
2. 主动消息检查：30 分钟到 2 小时一次
3. 日循环整理：一天一次

---

## 3. 四块职责定义

## A. 聊天主链

### 职责

- 接收用户聊天输入
- 直接调用大模型
- 返回聊天回复

### 规则

- 不经过小模型筛选
- 不做“值不值得回”的判断
- 一定回复

### 备注

RP 模式和普通日常聊天都属于聊天主链，只是 UI 和 prompt 结构不同。

---

## B. 被动唤醒 / 事件注入

### 来源示例

- iOS 快捷指令
- 上传照片
- 发朋友圈 / 动态
- 打开某个 App
- 外部 webhook
- 未来的 Telegram / MCP 外部事件

### 目标

收到事件后，不直接叫大模型。

先让小模型判断：

- 这件事值不值得继续处理
- 要不要通知大模型
- 还是静默丢掉

### 小模型输出建议

```json
{
  "should_handle": true,
  "should_notify_llm": false,
  "reason": "只是普通打开应用，无需回应",
  "message_hint": ""
}
```

### 本层结果

可能有三种：

1. 静默丢弃
2. 只写活动 / 更新状态，不说话
3. 交给大模型继续生成回应

### 设计原则

- 被动事件不一定值得回应
- 先筛，再决定是否上大模型
- 不要让“任何小事都唤醒大模型”

---

## C. 主动消息检查 / 随机唤醒

### 目标

不是直接发消息。

而是定时由小模型扫一遍状态，判断“现在要不要主动说话”。

### 输入

- summary
- recent activity
- cooldown
- companion_state
- 最近聊天时间
- 最近主动消息时间
- 当前 agent 风格

### 小模型输出建议

```json
{
  "should_proactive": true,
  "reason": "用户已沉默较久，且最近存在未闭合话题",
  "message_hint": "可以轻提上次没聊完的话题"
}
```

### 规则

- 只有 `should_proactive = true` 时，才交给大模型写真正内容
- 小模型不直接写最终消息正文
- 大模型只负责真正要发出去的话

### 推荐频率

- 30 分钟兜底一次，或
- 1 到 2 小时一次

### 设计原则

- 主动消息不是每次都发
- 先检查，再决定
- 大模型不是巡逻器，只是成文器

---

## D. 意识循环 / 日循环整理

### 目标

这是最重的一层。

它不是“随机看看要不要说话”，而是低频深整理。

### 小模型先做的事

- 清理 ephemeral
- 整理 recent activity
- 汇总 memory 候选
- 生成状态快照
- 更新 companion_state summary

### 第二步再决定

要不要把整理结果交给大模型去做：

- diary
- 更完整的总结
- 更深层的状态文本

### 规则

- 不是每次都写大段
- 先整理，再决定是否深写

### 推荐频率

- 一天一次就够

### 设计原则

- 日循环重在沉淀，不重在输出
- 小模型先做结构化整理
- 大模型只接“值得写”的结果

---

## 4. companion_state 与 memory 的关系

这两者不能混为一谈。

### companion_state

定位：

- 短中期状态快照
- 当前关系、情绪、最近话题、进行中事项

特点：

- 更新频率相对高
- 会被主动消息检查直接消费
- 偏“现在是什么状态”

### memory

定位：

- 长期沉淀
- 偏好、设定、重要事件、稳定印象

特点：

- 更新频率更低
- 不能因为每次状态整理都写
- 要先判断“值不值得进入长期记忆”

### 原则

- state 更新可以更勤
- memory 写入必须更克制

---

## 5. 当前建议落地顺序

按风险和收益排：

1. 先跑稳日循环整理
2. 再补主动消息检查
3. 最后接被动唤醒 / 事件注入

原因：

- 日循环最收敛，边界最清楚
- 主动消息只是在 state 之上做判断
- 事件注入来源最散，最后接最稳

---

## 6. 各层建议的模型分工

### 聊天主链

- 大模型直连

### 被动唤醒

- 小模型判断
- 需要时再叫大模型

### 主动消息检查

- 小模型扫状态
- 需要时再叫大模型写消息

### 日循环整理

- 小模型先整理
- 必要时再叫大模型写 diary / 深总结

## 8. 本文档要约束什么

以后新增功能时，先问自己放哪一层：

- 聊天必回：放聊天主链
- 外部小事注入：放被动唤醒
- 想不想主动说话：放主动消息检查
- 做整理、沉淀、写日记：放日循环

别再把这三层搅成一锅。

这锅之前已经搅过一次了，够蠢了。

## 9. 当前实现状态 - 2026-05-01

### 已完成：activity_events / event_gate 第一阶段

- 已新增 `activity_events` 短期活动流。
- 已提供 `POST /api/activity-events` 供 iOS 快捷指令等外部入口上报。
- 已提供 `GET /api/activity-events/recent` 供调试和后续前端展示。
- 已实现 5 分钟同类事件去重。
- 新事件写入后会调用 `event_gate` 轻量筛选。
- 筛选结果会回写到 activity_events：`gate_should_handle / gate_should_notify_llm / gate_message_hint / gate_reason`。
- consciousness 会读取最近活动，并写入 snapshot 的 `background_activity_candidates`。
- proactive 会读取这些 recent activity，作为主动消息判断的短期上下文。

### 已完成：daily_loop 安全二阶段

- 新增手动触发接口：`POST /api/consciousness/daily-loop/trigger`。
- 新增读取接口：`GET /api/consciousness/daily-loop/latest`。
- 日循环会读取 companion_state、近 24 小时 activity_events、高温记忆、最近主动消息。
- 会生成整理报告和 diary/memory 候选。
- `should_write_diary=true` 时只写 private diary 草稿。
- `should_write_memory=true` 时只写 `cot_logs` 的 memory_candidate 候选日志，不直接写正式 memory。
- 模型失败时保存 fallback 报告，避免错误沉淀。

### 仍未完成

- 被动唤醒已有小模型轻判断层：`should_handle / should_notify_llm / message_hint`，但还没接后续动作。
- 主动消息检查已接入小模型轻报告：`should_proactive / reason / message_hint`，后续需要真实数据调参。
- 日循环还没有把 memory_candidate 自动转成正式 memory。
- 前端活动日志已接 `/api/activity-log/recent`，还需要继续收筛选和显示细节。

### 下一步优先级

1. 配 iOS 快捷指令真实上报 activity_events。
2. 观察 event_gate / proactive_gate 轻报告拒绝率和误触发。
3. 手动跑 daily_loop 看草稿/候选质量，再决定 memory_candidate 如何进入正式 memory。
4. 继续收活动日志筛选和显示细节。
